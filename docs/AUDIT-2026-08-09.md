# PHPTRAVELS v10 — Platform Audit

**Date:** August 9, 2026
**Scope:** Full codebase — features, modules, APIs, security, correctness, performance, structure, code quality
**Method:** Static analysis (grep/AST-style pattern scans) across 73,203 lines of PHP, plus live probing of the running instance at `localhost/v10` and live inspection of the MySQL schema.

---

## 1. Executive Summary

v10 is a large, feature-complete travel platform: **14 booking verticals**, **42 supplier integrations**, **872 route registrations**, **61 database tables**. The architecture (Routing-Views, lazy route loading, cache-booking flow, shared invoice/payment components) is coherent and the recent code is genuinely well-commented.

The problems are not architectural — they are **operational safety and scale readiness**. Three things stand out:

1. **`install/reset.php` is publicly reachable with no authentication and truncates the database.** This is a site-destruction button on every deployed install.
2. **The mobile API can be accessed without an API key** by any client that first loads a normal web page (session-flag bypass).
3. **The `bookings` table has no indexes beyond the primary key.** It works today at 0 rows; it will degrade badly in production.

Everything else is meaningful but secondary.

### Scorecard

| Area | Score | Notes |
|---|---:|---|
| Feature completeness | 9/10 | 14 verticals, end-to-end booking + payment + invoicing |
| Architecture & routing | 8/10 | Clean RV pattern, lazy loading is a genuinely good optimisation |
| Security | **3/10** | Public DB-reset script, API auth bypass, 35 POST files with no CSRF |
| Correctness | 6/10 | 13 guaranteed-fatal calls, 5 unwrapped module files, dead theme system |
| Performance (backend) | 6/10 | Fast now, but missing indexes and unbounded log tables |
| Performance (frontend) | **3/10** | Tailwind Play CDN in production + jQuery + Alpine; 154 KB HTML for a login page |
| Code quality / DRY | 5/10 | ~12,400 lines of near-duplicate booking logic |
| Documentation | 8/10 | README is a strong, maintained scope doc |

**Overall: 6/10 — strong product, unsafe to run unhardened in production.**

> **Current instance state:** `settings.user_restriction` is `1`, so the site is presently locked to logged-in users. Frontend benchmarks below were therefore taken against `/login`.

## 3. CRITICAL — fix before any production deploy

### C1. `install/reset.php` is a public, unauthenticated database wipe

**File:** `install/reset.php:42-48`

The protection is shipped **commented out**:

```php
// SECURITY: Uncomment to require confirmation
// if (!isset($_GET['confirm']) || $_GET['confirm'] !== 'yes_reset_now') {
//     die('Access Denied. Please add ?confirm=yes_reset_now to URL');
// }
```

The script then runs on a plain `GET`, calls `TRUNCATE TABLE` in a loop (`install/reset.php:312`), deletes cache files (`:277`), and re-seeds users with hardcoded password hashes (`:374`, `:410`).

**Verified live:** `GET /v10/install/reset.php` → **HTTP 200**. There is no `install/.htaccess`.

**Impact:** any visitor — or any crawler that follows a link — can destroy every booking, user and setting on a live install. Even the commented-out guard is inadequate (a URL parameter is not authentication).

**Fix:** require `ADMIN_AUTH()`; better, delete/ignore the whole `install/` directory post-install and add an `install/.htaccess` deny rule plus an "installation complete" lock file check.

---

### C2. Mobile API authentication can be bypassed via the web-session flag

**Files:** `modules/helpers.php:687-726`, `index.php:149`

`index.php` marks *every* non-API page load as a trusted web client:

```php
if (strpos($requestUri, '/api/') === false && strpos($requestUri, '/modules/') === false) {
    $_SESSION['is_web_client'] = true;
}
```

`verifyApiKey()` then skips key validation entirely when that flag is set:

```php
$isOwnWeb = !empty($_SESSION['is_web_client']);
if (!$isOwnWeb) { /* ...only here is the key checked... */ }
```

**Attack:** `GET /` (sets the flag on your session cookie) → reuse that cookie against any of the 148 `/api/*` endpoints → full API access with no key.

**Three further weaknesses in the same function:**

| Issue | Line | Risk |
|---|---|---|
| Fail-open: `if (empty($serverApiKey)) return;` | `:692` | No key configured ⇒ **all APIs public** |
| Key accepted from `$_GET['api_key']` | `:722` | Leaks into access logs, `Referer`, browser history |
| `$clientApiKey !== $serverApiKey` | `:725` | Non-constant-time compare; use `hash_equals()` |

**Fix:** drop the session bypass (the web frontend should send the key server-side, or use a separate same-origin CSRF-token path); fail *closed* when no key is configured; header-only; `hash_equals()`.

---

### C3. No rate limiting on the web app or the mobile API

`RateLimiter` exists and is well built — but it is wired into **`modules/index.php` only** (the supplier gateway). It does not protect:

- the **148 `/api/*` endpoints** (login, signup, booking, password reset)
- `/login`, `/signup`, `/forgot-password` on the web frontend

Account lockout *does* exist (`app/routes/users/loginRoutes.php:127-237`, `login_attempts` + `locked_until`, 5 attempts), which blunts single-account brute force. It does **not** stop credential stuffing across many accounts, signup spam, or password-reset email flooding.

**Fix:** reuse the existing `RateLimiter` class in `app/routes/_routes.php` for `/api/*`, and per-IP on the auth routes.

## 4. HIGH

### H1. 35 of 56 non-API POST route files have no CSRF validation

Including nearly all admin CRUD: `usersRoutes`, `bookingsRoutes`, `gatewaysRoutes`, `promoCodesRoutes`, `staysRoutes`, `flightsRoutes`, `toursRoutes`, `umrahRoutes`, `carsRoutes`, `visaRoutes`, `blogsRoutes`, `menusRoutes`, `transactionsRoutes`, `creditsRoutes`, `updatesRoutes`, plus `ajaxRoutes.php` (the generic delete endpoint).

A `CSRF` class exists and is used in 43 places — coverage is simply incomplete. `ajaxRoutes.php` is the sharpest edge: it accepts `{action:'delete', table, id}` and validates the table name only by regex.

**Fix:** enforce centrally rather than per-route — call `CSRF::verifyRequest()` for all non-API POSTs from `index.php`, then remove the ad-hoc per-file checks.

### H2. `$db->error()` does not exist in Medoo 2.x — 13 guaranteed fatals

**Verified by reflection:** `Medoo\Medoo::error` is a **property**, not a method. Every call site raises `Error: Call to undefined method`.

| File | Lines |
|---|---|
| `app/routes/admin/settingsRoutes.php` | 1086, 1638, 1868, 2019, 2160, 2240 |
| `app/routes/admin/usersRoutes.php` | 166, 205, 248 |
| `app/routes/admin/modulesRoutes.php` | 161, 273 |
| `modules/flights/sabre/actions/issue.php` | 420 |

These sit inside DB-error branches, so the **error handler itself crashes** — turning a recoverable failure into a white screen with no diagnostics. `usersRoutes.php:166` is worse: `$db->error()[0] == '00000'` is on the *success* path of user creation.

**Fix:** `$db->error` (property), or better `$db->pdo->errorInfo()`.

### H3. Five module files execute at include time (the CarTrawler-class bug)

`modules/index.php` includes every supplier file on every gateway request, so any top-level code runs on unrelated requests — the exact failure that took down all module APIs in v3.6.

- `modules/flights/travelpayouts/actions/issue.php`, `void.php`, `cancel.php`, `refund.php`
- `modules/rail/train/search.php`

The travelpayouts four are currently harmless stubs (`// TODO: Implement`), but they are live landmines: the moment someone implements them without a `$router->post()` wrapper, every module API breaks. `rail/train/search.php` needs manual review.

**Fix:** wrap all five; add a CI guard that fails if any file under `modules/*/*/` contains top-level executable statements.

### H4. SQL injection in two supplier search paths

```php
// modules/flights/amadeus/search.php:350
$pdo->query("SELECT * FROM `flights_airlines` WHERE `code` = '$seg2->carrierCode'")
// modules/flights/seeru/search.php:7,13
$pdo->query("SELECT * FROM `flights_airlines` WHERE `code` = '$airline_code'")
$pdo->query("SELECT * FROM `flights_airports` WHERE `code` = '$airport_code'")
```

The interpolated values come from **supplier API responses** — third-party data treated as trusted. A compromised or hostile upstream (or a MITM on a non-pinned endpoint) gets SQL execution.

Also of note: `TRUNCATE TABLE $table` / `DROP TABLE IF EXISTS $table` with interpolated names in six content-import files (`hotelbeds:1924,1954`, `hotelston:779`, `agoda:345`, `ratehawk` ×2). Currently fed from internal arrays, but one refactor away from being user-reachable.

**Fix:** prepared statements everywhere; whitelist table names against a fixed array.

### H5. `eval()` in the CRUD row formatter

**File:** `app/lib/crud.php:403` — `$result = @eval("return $expression;");`

Column values are substituted with `addslashes()` before evaluation, which is *mostly* adequate for single-quoted PHP strings, so this is not currently exploitable via DB content. But it is `eval()` on a string built from database values, wrapped in `@` to hide failures, in a library used by every admin table. Any future path where a template string comes from the DB or a request is instant RCE.

**Fix:** replace with a small whitelist of formatter callbacks; the row-format DSL only needs a handful of functions.

### H6. Reflected XSS in admin user form

**File:** `app/views/admin/users/user.php:105`

```php
<input type="hidden" name="current_tab" value="<?= $_GET['tab'] ?? 'profile' ?>">
```

Unescaped inside an attribute — `?tab="><script>…` breaks out. Requires an admin session, so it is a privilege-escalation vector (admin-targeted CSRF+XSS chain), not anonymous.

**Fix:** `htmlspecialchars()`. Then sweep views for the same pattern.

### H7. Session cookies are not hardened

No `session_set_cookie_params()` anywhere: `HttpOnly`, `Secure` and `SameSite` are left to php.ini defaults. `session_regenerate_id(true)` is correctly called on login (`app/lib/auth.php:114`).

**Fix:** in `config.php` before `session_start()`:

```php
session_set_cookie_params([
    'httponly' => true,
    'secure'   => !empty($_SERVER['HTTPS']),
    'samesite' => 'Lax',
]);
```

## 5. Performance

### P1. Frontend is the biggest win available

**Measured:** `/login` = **153,844 bytes of HTML**, ~85 ms server time. For a login page.

`app/views/includes/header.php:211-221` loads **three UI runtimes**:

| Resource | Problem |
|---|---|
| `https://cdn.tailwindcss.com` (`:211`) | **Render-blocking, no `defer`.** This is the Play CDN — a full Tailwind compiler running in the browser on every page load. Tailwind's own docs say never use it in production. |
| `assets/js/tailwind.js` (`:216`) | A *second* Tailwind payload alongside the CDN one |
| `https://code.jquery.com/jquery-3.7.1.min.js` (`:220`) | 3rd-party origin; also the cause of the documented Alpine-loads-before-jQuery init bug |
| `https://cdn.jsdelivr.net/…/alpinejs` (`:219`) | 3rd-party origin |

There is **no `package.json` and no `tailwind.config.js`** — no build step exists.

Also: `<title>` and all meta tags are emitted **after** the script block (`:222+`), delaying the browser's first meaningful parse.

**Fix (highest ROI in the whole audit):**
1. Add a Tailwind build step; ship one purged CSS file (typically 10–30 KB vs. the ~400 KB in-browser compiler).
2. Self-host Alpine and jQuery — or drop jQuery entirely (only a few call sites remain).
3. Move `<title>`/meta above scripts; `defer` everything.

Expect a large LCP/TBT improvement and a ~120 KB drop in HTML weight.

### P2. `bookings` has no index except PRIMARY

**Verified live against the schema.**

| Table | Indexed columns | Risk |
|---|---|---|
| `bookings` | `id` only | **Every** lookup is by `invoice_id`, `user_id`, `module`, `booking_status`, `pnr`, `created_at` → full scan |
| `logs_bookings` | `id` only | Draft lookup is `WHERE hash = ?` → full scan on the checkout hot path |
| `logs_users` | `id` only | Unbounded activity log, scanned |
| `modules` | `id` only | Queried by `(type, status)` on every request |

Invisible today (0 rows) and crippling at 100k bookings.

```sql
ALTER TABLE bookings
  ADD INDEX idx_invoice (invoice_id),
  ADD INDEX idx_user (user_id),
  ADD INDEX idx_module_status (module, booking_status),
  ADD INDEX idx_created (created_at),
  ADD INDEX idx_pnr (pnr);
ALTER TABLE logs_bookings ADD UNIQUE INDEX idx_hash (hash);
ALTER TABLE logs_users ADD INDEX idx_user_date (user_id, created_at);
ALTER TABLE modules ADD INDEX idx_type_status (type, status);
```

(The README has recommended `idx_type_status` on `modules` since v2.4; it was never applied.)

### P3. Abandoned booking drafts are never cleaned up

`logs_bookings` rows are deleted only on **successful** submit (`app/routes/api/*/bookingRoutes.php`). Every abandoned checkout — the majority of sessions — leaves a permanent row containing a full JSON booking draft.

**Fix:** a cron pass deleting drafts older than the `booking_expiry_time` setting. The cron route infrastructure already exists.

### P4. Application cache is disabled by default

`index.php:31` — `appCacheRemember()` is a no-op unless `APP_DB_CACHE_ENABLED=1`. So every request re-runs 4 queries (settings, languages, currencies, modules) that change perhaps weekly.

The comment says it is off "so DB changes are reflected immediately" — reasonable for development, wrong for production. Ship it on with a cache-bust on settings save.

### P5. Minor

- **878 `error_log()` calls** — largely ungated; heavy disk I/O under load. Gate verbose ones behind a debug flag (the pattern already exists in the Travelport module).
- **291 `@` error suppressions** — hides real failures and still costs the error handler.
- 8 N+1 query sites in views (`app/views/modules/blogs/listing.php`, `cars/listing/cars.php`, `esim/esim-search.php`, and the bus/cars booking pages).

## 6. Code Quality & Structure

### Q1. ~12,400 lines of near-duplicate booking logic

| File | Lines |
|---|---:|
| `app/routes/flights/bookingRoutes.php` | 1,172 |
| `app/routes/api/flights/bookingRoutes.php` | 1,171 |
| `app/routes/api/ferries/bookingRoutes.php` | 1,106 |
| `app/routes/api/tours/bookingRoutes.php` | 960 |
| `app/routes/api/stays/bookingRoutes.php` | 913 |
| …13 files total | **12,372** |

The web and API variants for the same vertical are near-identical (flights: 1,172 vs 1,171), and every vertical re-implements the same pipeline: validate → resolve guest/user → markup + tax → commission → insert `bookings` → clear draft → notify → redirect to invoice.

This is why the same bug had to be fixed 3× (`promo_code`/`promo_codes`, v3.6) and 10× (`Prn` casing, v3.2).

**Fix:** one `BookingService` with per-module adapters. Realistic target: 12,400 → ~3,000 lines. Highest maintainability ROI in the codebase.

### Q2. The theme system is dead code

`app/lib/ThemeManager.php` reads/writes `themes/` — **the directory does not exist.** `getAvailableThemes()` returns empty; `createTheme()` throws. Yet `app/routes/admin/settingsRoutes.php:114-131` still exposes switch/create/delete/reset actions, and the README documents it as a feature. Views actually live in `app/views/`.

**Fix:** either delete ThemeManager and the admin tab, or reimplement it against `app/views/`. Do not leave it half-wired.

### Q3. Inconsistent promo-code field naming

`promo_code` (singular) still appears in `ai/tripBookingRoutes.php:1676`, `api/bus:434`, `api/cars:606`, `api/esim:249`, `api/ferries:853` — as *input* keys, while the DB column is `promo_codes`. These are currently correct but the naming collision is exactly what caused the v3.6 outage. Normalise.

### Q4. Other

- **10 TODO/FIXME** markers; 4 leftover `var_dump`/`print_r`.
- `install/` ships `import.php`, `translate.php`, `umrah.php`, `template.php` — dev utilities, publicly reachable.
- Commenting quality is genuinely good in recent code (bus, rail, user-restriction). Older supplier modules are sparse. Worth a consistency pass, not urgent.
- 6 catch-all routes (`/stays/(.*)`, `/tours/(.*)`, `/bus/(.*)`, `/umrah/(.*)`, …) rely on include order in `_routes.php`. It is correct today and commented — but it is load-bearing ordering with no test. A single reordering breaks booking pages silently.

## 7. What is genuinely good

Worth preserving through any refactor:

- **Lazy route loading** (`_routes.php:13-22`) — admin/API files parse only when targeted. Real, measurable win on shared hosting.
- **The cache-booking flow** — uniform `save-draft → hash → booking page → submit` across all verticals.
- **Shared invoice/payment components** — one payment callback path, one PDF generator.
- **Self-healing schema helpers** (`ensureCurrencyUpdateSchema`, `ensurePassportAiSchema`, `ensureUserRestrictionSchema`) — clients upgrade without manual SQL.
- **`RateLimiter`** — solid implementation, just under-deployed.
- **README as a maintained scope doc** — unusually good for a project this size.
- **Password handling** — `password_hash`/`password_verify` throughout, lockout after 5 attempts, `session_regenerate_id` on login.
- **Upload validation** — `handleFileUpload()` checks real MIME via `finfo`, not just the extension.
